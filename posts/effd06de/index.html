深入理解虚拟列表：从固定高度到不定高度前端实现（附完整代码）

|浏览量:

本文转载自 nanchen_J（CSDN），原标题《深入理解虚拟列表：从固定高度到不定高度前端实现（附完整代码）》，作者：nanchen_J，发布时间：2025-11-17。

虚拟列表（Virtual List），也叫虚拟滚动（Virtual Scrolling / Windowing），是前端性能优化中最经典、最实用的技术之一。当我们需要渲染成千上万条数据时，如果直接把所有 DOM 节点一次性创建并插入页面，浏览器会面临巨大的内存压力和重排重绘开销，导致页面卡顿、滚动掉帧，甚至直接崩溃。

虚拟列表的核心思想非常简单：在任意时刻，只渲染可视区域 + 少量缓冲区的真实 DOM 节点，其余部分用一个占位容器撑起总高度。当用户滚动时，动态计算当前应该显示哪些项，回收不可见的 DOM，复用或新建可见的 DOM，从而把 DOM 节点数量控制在几十个的量级，无论数据总量是 1 万还是 100 万，性能都几乎一致。

今天我们通过两个完整、可直接运行的纯前端示例，来彻底拆解虚拟列表的实现原理：

  1. 固定高度版本（最简单、最高效，适合绝大多数场景）
  2. 不定高度版本（更通用，但实现复杂度显著提升）

两个例子都只用了原生 HTML + CSS + JavaScript，没有任何框架，代码量极少，却把核心难点全部覆盖。读完本文，你将彻底明白虚拟列表为什么快、怎么自己从零手写、以及在实际项目中该如何选择。

一、固定高度虚拟列表完整解析

1. 页面结构与样式

核心结构只有两层：

  • .viewport：可视窗口，固定高度（这里是 480px），overflow: auto，真正发生滚动的容器。
  • .inner：内部占位容器，高度等于 总条数 × 单项高度，它负责把滚动条「撑长」，让用户感觉有成千上万条数据。

2. 核心变量与数据结构

buffer 是非常重要的体验优化参数。当用户快速滚动时，浏览器可能来不及渲染新出现的区域，会闪现白块。提前多渲染几条，就能完美解决这个问题。实际项目中通常取 5~10。

3. 数据生成与占位高度设置

7. 固定高度版本小结

  • DOM 节点数量 ≈ (视口高度 / 项高) + 2×buffer，通常 30~60 个
  • 滚动计算复杂度 O(1)
  • 内存占用极低，滚动丝滑如丝
  • 适用场景：99% 的长列表（聊天记录、商品列表、日志列表……几乎都可以设计成固定或近似固定高度）

二、不定高度虚拟列表完整解析

在实际项目中，我们常常会遇到每条数据高度不一致的情况（比如微博、朋友圈、评论区，带图、展开收起等）。这时固定高度的技巧就失效了，我们必须想别的办法。

1. 核心难点

  • 无法用 scrollTop / itemHeight 直接算出当前第一条是谁（因为高度未知）
  • 无法用 index * itemHeight 计算某条的准确位置
  • 必须提前知道每一项的真实高度，才能正确设置 top 和总高度

7. 不定高度版本小结

  • 需要提前知道所有项的高度（可以在数据加载完后一次性测量）
  • 使用累计位置数组 + 二分查找实现 O(log N) 的索引查找
  • DOM 节点数量依然只有几十个，性能优秀
  • 内存占用比固定高度版稍高（多了两个长度为 N 的数组），但对现代浏览器完全不是问题
  • 适用场景：微博、朋友圈、复杂 feed 流等真正高度不可预知的情况

三、两个版本的深度对比

维度 固定高度版本 不定高度版本
计算可见项复杂度 O(1) O(log N) + O(k)（k 为可见项数）
是否需要预知高度 否 是（必须提前测量或预估）
实现难度 ★☆☆☆☆ ★★★☆☆
性能（理论） 最优 稍逊但实际无感知差异
内存占用 最低 稍高（两个 N 长度数组）
适用场景 99% 的业务场景 高度完全不可控的复杂 feed
跳转到指定项 O(1) O(1)（直接用 positions[idx]）
动态插入/删除 简单（只需调整总高） 复杂（需重新计算后续 positions）

结论：在能用固定高度的情况下，坚决使用固定高度实现，性能极致、代码最简。不行时再上不定高版本。

四、实际项目中的进一步优化（生产级实践）

1. DOM 节点复用（对象池）

示例中每次滚动都 innerHTML = '' 再重建，实际上会频繁创建/销毁 DOM。生产环境应该：

渲染时从池中取，用完后回收，只改 textContent/top/height，避免 GC 压力。

2. 高度缓存与动态变化处理

在真实项目中，图片加载、用户展开收起、字体加载都可能导致高度变化。我们通常做法是：

  • 维护一个 heightCache Map<number, number>
  • 项真正渲染到可视区时，用 offsetHeight 测量真实高度
  • 如果与缓存不同，更新 heightCache[i] 和后续所有 positions[i+k]
  • 触发重渲染

这部分代码会稍复杂，但完全可控。

3. React/Vue 中的实现思路

React 中最流行的就是 react-window 和 react-virtualized，底层原理与本文完全一致。

如果你想自己手写 React 版，只需要：

  • 用 useRef 保存 viewport 和 inner
  • 用 useEffect 监听 scroll
  • 用 useMemo 计算 start/end
  • 用数组 map 渲染可见项，key={item.id}，style={{ position: 'absolute', top: positions[i], height: heights[i] }}

代码量比原生版还少。

4. 关于预估高度的技巧

有些场景无法提前知道所有高度（比如无限加载）。常见做法是：

  • 给每项一个预估高度（比如 100px）
  • 真正渲染后测量真实高度
  • 如果差值超过阈值，更新 positions 并修正滚动位置（scrollTop += delta）

这样可以实现「先快速显示 → 再精确修正」的丝滑体验，Instagram、Twitter 都是这么干的。

五、性能实测数据（可自行验证）

在 Chrome 上测试 10 万条数据：

实现方式 DOM 节点数 内存占用 滚动帧率 加载时间
普通全部渲染 100,000 ~850MB 卡死 >8s
固定高度虚拟列表 ~58 ~45MB 60fps <80ms
不定高度虚拟列表 ~62 ~68MB 60fps <120ms

差距是毁灭性的。

六、总结

虚拟列表是前端性能优化的「核武器」之一，实现原理其实非常简单：

  • 用一个高高的占位容器撑起滚动条
  • 只渲染可视区附近的真实 DOM
  • 滚动时快速计算当前该显示哪段数据
  • 固定高度用除法，不定高度用二分查找 + 预计算位置

掌握了这两个示例，你就彻底掌握了虚拟列表的全部精髓。以后无论在原生项目还是 React/Vue/Angular/Svelte 中遇到超长列表，都可以轻松手写一个丝滑无比的实现。

代码已经完整贴出，直接复制到 HTML 文件就能运行和调试。建议你把条数改到 100 万、1000 万去看效果，你会彻底相信：前端性能优化，有时候真的就是这么简单而粗暴有效。
