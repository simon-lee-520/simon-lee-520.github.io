我把前端开发 SOP 写进 Skill，Codex 终于不乱发挥了

转载发表于2026-04-22|更新于2026-04-22|AI
|浏览量:

本文转载自 Kryon 微信公众号，原标题《我把前端开发 SOP 写进 Skill，Codex 终于不乱发挥了》。

我以前让 Codex 改前端页面，最常说的一句话是：

按我们项目的习惯改，别乱发挥。

这句话听起来很合理，实际等于没说。

因为 Codex 不知道“我们项目的习惯”到底是什么。

它不知道你们页面开发前要先看哪几个目录，不知道组件能不能拆，不知道接口字段能不能动，也不知道你说的“完成”到底是代码能跑、页面能看，还是已经跑过检查命令。

所以它会按自己的理解来。

第一轮能写出来。

第二轮开始顺手抽组件。

第三轮把样式规范也一起重做。

最后你不是在验收代码，而是在把 AI 拉回正轨。

后来我发现，前端用 Codex 最需要的不是一句更厉害的 Prompt，而是一份更清楚的开发 SOP。

把 SOP 写进 Skill 之后，Codex 才开始像一个“知道流程的新同事”。

为什么 Codex 会乱发挥

很多前端任务从表面看很简单。

比如：

把用户列表页优化一下。

但这句话背后有一堆隐含规则：

隐含规则 如果没说清楚，Codex 可能怎么做
复用现有组件库 自己写一套按钮、弹窗、表格
不改业务语义 顺手调整接口字段、状态结构
保持页面风格一致 做出一个和全站不一样的新 UI
小步修改 把页面拆成好几个新文件
改完要验证 只说“已完成”，不跑命令

这些规则不是某次需求的细节。

它们是团队开发方式。

如果每次都靠一句 Prompt 补充，迟早会漏。

所以真正应该做的是：把这些隐含规则显性化，写成 Codex 每次都能读懂的流程。

OpenAI Academy 的 Skills 说明里有一个关键点：Skill 不是单句提示词，而是可复用、可分享的工作流。它可以用 SKILL.md 记录任务说明、操作步骤、资源和输出格式。OpenAI Help Center 也提到 Codex App 支持 skills 和 automations。

换到前端开发里，Skill 最适合承载的不是“帮我写一个按钮”，而是：

做一个前端任务时，你应该按什么顺序理解、修改、验证和交付。

也就是 SOP。

前端开发 SOP 应该管什么

别把 SOP 写成公司制度。

那种文档写得越厚，Codex 越难抓重点。

前端开发 SOP 最好只管 5 件事：

  1. 1. 输入：开始前需要哪些信息。
  2. 2. 边界：哪些文件、行为、依赖不能随便改。
  3. 3. 步骤：先读什么，再改什么，最后查什么。
  4. 4. 验收：功能、样式、状态、响应式、命令怎么检查。
  5. 5. 回复：最后必须把改动、验证和风险说清楚。

这五件事写清楚，就能减少大部分跑偏。

前端开发 SOP 的 5 个固定节点

一份可以直接复制的 SKILL.md

下面这份可以直接当起点。

建议文件放在类似这样的目录：

skills/frontend-dev-sop/SKILL.md

正文可以用中文，name 用英文短标识就行。

---  
name: frontend-dev-sop  
description: 当前端开发任务需要按团队 SOP 完成时使用，包括需求理解、改动边界、页面实现、状态补齐、响应式检查和交付说明。  
---  

# 前端开发 SOP  

## 使用场景  

当用户要求开发、修改、优化、重构一个前端页面或组件时，先按这个流程执行。  

适合任务：  

- 新增业务页面  
- 修改已有页面  
- 优化 UI 和交互状态  
- 拆分组件但不改变行为  
- 修复前端缺陷  
- 做合并前自查  

## 开始前先读  

不要立刻改代码。先阅读这些信息：  

1. 用户给出的需求、截图、设计稿或链接。  
2. 相关路由、页面组件和子组件。  
3. 项目已有 UI 组件、样式变量、布局模式。  
4. 接口类型、Mock 数据、状态管理和错误处理方式。  
5.`package.json` 里的脚本命令。  
6.`AGENTS.md`、README 或附近目录里的项目规则。  

如果信息缺失，但可以从代码里推断，就先推断并说明依据。  

如果缺失信息会影响行为判断，再向用户确认。  

## 改动边界  

默认遵守这些边界：  

- 不引入新的 UI 库。  
- 不新增生产依赖，除非用户明确要求。  
- 不重写无关页面和共享组件。  
- 不改变接口字段语义。  
- 不删除已有交互状态。  
- 不把局部样式问题扩大成架构重构。  
- 不为了通过类型检查随便使用 `any`。  
- 不在未确认的情况下修改鉴权、支付、权限、埋点等高风险逻辑。  

## 开发步骤  

1. 复述你理解的任务目标。  
2. 列出需要修改的文件范围。  
3. 找到最小可行改动路径。  
4. 优先复用现有组件和工具函数。  
5. 小步修改，不做无关重构。  
6. 补齐加载态、空状态、错误态、禁用态、长文本和移动端布局。  
7. 修改后运行项目中最接近的检查命令。  
8. 如果命令不能运行，说明原因和替代验证方式。  

## 验收清单  

交付前检查：  

- 需求目标是否完成  
- 用户可见行为是否符合预期  
- 桌面端和移动端是否没有明显溢出  
- 长文本、空数据、接口失败是否有处理  
- TypeScript 类型是否没有被绕过  
- 样式是否复用现有设计系统  
- 是否运行了 lint、typecheck、test 或 build  
- 是否说明了未覆盖风险  

## 最终回复格式  

请按下面结构回复：  

### 改动  

- 修改了哪些文件  
- 每个文件解决什么问题  

### 验证  

- 运行了哪些命令  
- 命令结果如何  
- 页面或交互检查了什么  

### 风险  

- 哪些地方没验证  
- 哪些地方需要用户确认

这份 Skill 的核心不是“让 Codex 更听话”。

它真正解决的是：让 Codex 知道什么叫“按前端开发流程完成”。

SOP 里最重要的是边界

很多人写 Skill，只写“你要做什么”。

但前端开发里，更重要的是“你不要做什么”。

因为 Codex 的问题往往不是不会改，而是改太多。

比如你让它优化一个表单页，它可能顺手：

  • • 把表单库换掉。
  • • 把字段命名重写。
  • • 把校验逻辑移到新文件。
  • • 把 UI 样式改成另一套风格。
  • • 把没有问题的状态管理也一起调整。

这些动作单看都像“优化”。

但放到真实项目里，都是风险。

所以 SOP 里一定要写边界：

## 改动边界  

- 只改和当前任务直接相关的文件。  
- 优先修局部问题，不主动扩大重构范围。  
- 不改变接口字段含义。  
- 不新增依赖。  
- 不替换设计系统组件。  
- 不修改无关测试快照。

这几行比“请写出高质量代码”有用得多。

因为它们会直接限制 Codex 的行动范围。

把“完成”定义清楚

另一个容易跑偏的地方，是“完成”的定义。

在 Codex 看来，代码写完可能就是完成。

在前端工程师看来，至少还要过几关：

验收项 要看什么
功能 用户路径是否能走通
状态 loading、empty、error、disabled 是否合理
样式 响应式、长文本、间距、层级是否稳定
类型 是否绕过 TypeScript
命令 是否跑了项目里最接近的检查
风险 没验证的地方有没有说清楚

这些东西也要写进 Skill。

否则 Codex 很容易在最后只回一句：

已完成优化。

这对工程协作没什么帮助。

更好的输出应该是：

改动：  
- 调整 UserList.tsx 的筛选区布局，复用现有 Button 和 Select。  
- 补齐空状态文案和接口失败提示。  

验证：  
- 已运行 pnpm astro check，0 errors。  
- 已在本地页面确认移动端不会横向溢出。  

风险：  
- 未连接真实接口，只基于现有 Mock 数据检查。

这才像一次可以交接的前端任务。

AGENTS.md 和 SOP Skill 怎么分工

如果你已经有 AGENTS.md，还需要这个 Skill 吗？

需要。

两者负责的东西不一样。

文件 负责什么 示例
AGENTS.md 项目长期规则 用 pnpm、目录结构、测试命令、禁改文件
frontend-dev-sop Skill 某类任务怎么执行 开发页面时先读什么、怎么改、怎么验收

简单说：

AGENTS.md 是项目说明书。

Skill 是任务执行手册。

一个前端项目里，比较舒服的搭配是：

AGENTS.md  
  记录项目事实：技术栈、命令、目录、规范  

frontend-dev-sop/SKILL.md  
  记录页面开发流程：输入、边界、步骤、验收  

frontend-code-review/SKILL.md  
  记录代码审查流程：风险、行为、类型、测试

这样 Codex 既知道项目怎么跑，也知道某类任务应该怎么干。

调用方式也要具体

有了 Skill，不代表 Prompt 可以随便写。

更推荐这种格式：

使用 $frontend-dev-sop 完成这个需求。  

需求：  
订单列表页筛选区太松散，需要改得更紧凑。  

约束：  
- 不改接口字段  
- 不换表格组件  
- 移动端不能横向溢出  

验收：  
- 空数据时显示明确提示  
- 跑项目检查命令

这段 Prompt 只描述“本次任务”。

通用流程交给 Skill。

这就是最理想的分工：SOP 固定，需求变化。

怎么迭代这份 Skill

不要指望第一版 Skill 就完美。

更实际的做法是，把它当成团队协作文件来迭代。

每次 Codex 跑偏，就问一句：

这次跑偏，是不是有一条规则应该写进 SOP？

比如：

跑偏现象 应该补进 Skill 的规则
总是重写组件 不把局部问题扩大成组件重构
总是忘记空状态 验收清单加入 empty/error/loading
总是新增依赖 新增依赖前必须说明必要性
总是不跑命令 最终回复必须列出验证命令
总是改无关文件 先列改动范围，只改直接相关文件

Skill 不需要一开始就写得很复杂。

它应该像代码一样，根据真实问题慢慢长出来。

常见问题

1. 这是不是把提示词换了个地方？

不是。Prompt 是一次性指令，Skill 是可复用流程。你可以把 Skill 理解成“长期有效的任务说明书”。

2. SOP 写得越细越好吗？

不是。太细会让 Codex 抓不住重点。先写输入、边界、步骤、验收、输出这五块就够了。

3. 一个 Skill 能不能覆盖所有前端任务？

不建议。frontend-dev-sop 适合页面和组件开发。Code Review、样式排查、性能优化最好拆成单独 Skill。

4. 中文 SKILL.md 会不会影响效果？

不会。团队规则本来就是中文表达更自然。建议 name 用英文，description 和正文用中文。

5. 什么时候需要问用户确认？

当缺失信息会影响业务行为、接口语义、权限、支付、数据写入或生产依赖时，应该确认。普通样式和局部组件实现，可以先基于代码上下文判断。

最后

Codex 乱发挥，很多时候不是它“不听话”。

是你没有告诉它：什么叫按流程做事。

前端工程里最值钱的经验，往往不是“这个按钮怎么写”，而是：

  • • 改之前先看什么。
  • • 哪些边界不能碰。
  • • 怎么判断任务做完。
  • • 怎么把风险说清楚。

这些东西如果只存在你脑子里，Codex 每次都要猜。

把它们写进 SKILL.md，它才有机会稳定复用。

所以，别再只说：

按我们项目习惯改。

把“项目习惯”写下来。

然后让 Codex 按 SOP 干活。
